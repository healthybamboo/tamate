# 解錠仕様

`tamate` は「開けないメモアプリ」である。書いたメモはすぐには読めず、開こうとしてから
一定時間待たないと本文が表示されない。この文書はその解錠まわりの決定事項をまとめる。
実装（`lib/features/memo/domain`）はこの文書を正とする。

## 用語

| 用語 | 意味 |
| --- | --- |
| ロック中 | まだ開こうとしていない状態。本文は読めない |
| 待機中 | 開こうとして計測が始まり、解錠条件を満たすまでの状態。本文は読めない |
| 解錠中 | 解錠条件を満たし、本文が読める状態 |
| 待機時間 | 解錠条件を満たすまでに必要な時間。メモごとに設定する |
| 閲覧可能時間 | 解錠してから再びロックされるまでの時間。アプリ共通の固定値 |
| 開封 | 本文が読める状態になること。回数と日時を記録する |
| 解錠コード | 作成時に1度だけ表示される4桁の数字。解錠に入力を求める（任意） |

## 決定事項

### 待機の起点

一覧からメモを開き、詳細画面の「開く」を押した時刻を起点とする。一覧を眺めているだけ、
詳細画面を開いただけでは計測は始まらない。起点は `Memo.waitStartedAt` として保存する。

### 待機時間

**メモごとに設定する。** 選択肢は次の4つで、既定値は3分。

- 1分 / 3分 / 5分 / 10分

1日待たせるような長さは、書いた側も読む気を失う。待たされている感覚が残るのは
せいぜい10分までなので、上限を10分にしてある。

待機時間は**作成時にのみ設定でき、作成後は変更できない**。あとから短くできると
「開けない」という前提が崩れるため。長さを変えたい場合はメモを作り直す。

### アプリを閉じたときの挙動

**待機は継続する。** 起点の時刻を保存しておき、残り時間は「現在時刻 − 起点」で毎回計算する。
アプリをバックグラウンドに送っても、プロセスが落ちても、端末を再起動しても待機は進む。

待機の中断は明示的な操作（待機画面の「待つのをやめる」）でのみ行う。中断すると計測は
リセットされ、次に開くときは最初から待ち直しになる。待機画面から戻るだけでは中断しない。

### 端末時刻の扱い

**端末時刻を進めて待機を飛ばせることは許容する。** データは端末内にしか無く、守るべき秘密が
あるわけでもないので、時刻の巻き戻し検知や単調増加クロックの導入は行わない。
残り時間は素直に `DateTime.now()`（実装上は差し替え可能な `Clock`）で計算する。

なお、時刻を巻き戻した場合は残り時間が伸びる。これも許容する。

### 解錠後

解錠してから**5分間だけ**読める。5分を過ぎると再びロック中に戻り、もう一度読むには
また待機が必要になる。閲覧可能時間はメモごとの設定ではなくアプリ共通の固定値
（`UnlockPolicy.openWindow`）とする。

再ロックの判定も「解錠時刻 + 5分 < 現在時刻」という時刻の計算だけで行う。したがって
アプリを閉じている間に閲覧可能時間が過ぎていれば、次の起動時にはロック中になっている。

### 編集

**解錠中のみ編集できる。** ロック中・待機中は本文の表示も編集も不可。
タイトルは常に表示・編集の対象外とし、一覧でも詳細でも表示する（どのメモか分からないと
開きようがないため）。削除は状態にかかわらずいつでもできる。

### 通知

待機を開始したときに、解錠予定時刻のローカル通知を予約する。待機を中断した場合と
メモを削除した場合は予約を取り消す。通知を許可しない選択をしてもアプリの機能は
通知以外すべて動作する。

通知は**解錠時刻ちょうどに出す**。「あと1分」と表示しておいて数分後に知らせるのでは
待つ体験が崩れるため、Android では正確なアラーム（`SCHEDULE_EXACT_ALARM`）を使う。
Android 14 以降はユーザーの許可が要るので、待機を始めるときに一度だけ求める。
許可されなかった場合は精度を落として予約する（通知は遅れることがあるが、画面上の
残り時間は現在時刻から計算しているのでズレない）。iOS はもともと時刻どおりに出る。

### 解錠コード（4桁）

作成時に**解錠コードを使うかどうか**を選べる。使う場合は4桁の数字をランダムに生成し、
**その場で1度だけ**表示する。控えを見る手段はアプリのどこにも用意しない。

解錠には、待機時間の経過に加えてこのコードの入力が必要になる。待機が終わると入力を
求める画面になり、正しく入力できたところで初めて本文が読める。

- 入力の失敗に回数制限は設けない。総当たりを防ぐ必要はなく、防ぎたいのは「覚えている
  つもりだった」という記憶の方だから
- 忘れたら二度と読めない。コードの再発行も、待ち直しによる回避もしない
- 再ロックされたあと読み直すときも、同じコードの入力を求める

### 開封の記録

本文が読める状態になった時刻を、メモごとに履歴として残す。回数はその件数で数える。

- 記録するのは「読めるようになった瞬間」。閲覧可能時間の内側で画面を出入りしても増えない
- 再ロックされたあとにもう一度開けば1件増える
- 履歴と回数は、ロック中でも詳細画面から見られる（本文ではないので隠す理由がない）

### 開封回数に応じた提案

開きすぎているメモには、詳細画面で提案を出す。どちらも「あとで」で閉じられる。
閉じてもその場で消えるだけで、次に開けばまた出る。

| 開封回数 | 出す提案 |
| --- | --- |
| 3回以上 | 待機時間を1段階のばす（1分 → 3分 → 5分 → 10分） |
| 5回以上 | 上に加えて、内容の見直しか削除 |

待機時間は作成後に変更できないのが原則だが、**この提案から伸ばす場合だけ例外**とする。
伸ばす方向にしか動かせないので、待つ体験を短くする抜け道にはならない。従うかどうかは
ユーザーが決める。

### 将来の仕掛け

待機時間以外の解錠条件（場所、回数など）を後から足せるよう、解錠条件は `UnlockRule`
として抽象化する。追加時は `UnlockRule` の実装を1つ増やし、`UnlockRule.fromJson` に
分岐を足すだけで済むようにする。複数の条件を組み合わせる場合は `AllOfUnlockRule` に
並べる（待機時間 + 解錠コードもこの形で表す）。

`UnlockRule` は解錠時刻を返せるとは限らない（解錠コードなど）。返せるのは時間の関門が
明ける時刻までで、通知もその時刻に予約する。実際に解錠が成立した時刻は
`Memo.unlockedAt` に記録し、閲覧可能時間の起点にする。

## 状態遷移

```
        ┌──────────── 待機を中断 / 閲覧可能時間が経過 ────────────┐
        │                                                        │
   ┌────┴─────┐   「開く」   ┌──────────┐   解錠条件を満たす   ┌────┴─────┐
   │ ロック中  │ ─────────→ │  待機中   │ ─────────────────→ │  解錠中   │
   └──────────┘             └──────────┘                     └──────────┘
```

状態はすべて `Memo`（`unlockRule` / `waitStartedAt` / `unlockedAt`）と現在時刻から
導出する。導出は `Memo.lockStateAt(DateTime now)` に閉じ込め、UI では時間計算をしない。

## 保存形式

`SharedPreferences` に JSON 配列で保存する。既存データにフィールドが無い場合の扱いは次の通り。

| フィールド | 欠けているとき |
| --- | --- |
| `unlockRule` | 既定の待機時間（10分）のルールとして読む |
| `unlockRule.type` が未知 | 同上（将来のバージョンで作られたデータを読んでもクラッシュしない） |
| `waitStartedAt` | `null`（ロック中） |
| `unlockedAt` | `null` |
| `openedAt` | 空の履歴（開封回数0回として扱う） |
